# 运行中强制升级（0.18.0）

日期：2026-10-31；发布修订：2026-11-03。状态：原 PR #150 未合入发布主线，现按当前用户确认准备
bridge-agent 0.18.0，配合已上线的 Relay 更新协议。

## 问题

客户端只在启动时检查一次更新。设备通常开机自启后一直运行，管理员在发布服务提高最低支持版本后，
正在运行的旧客户端要等下次重启才知道；启动检查失败后按离线模式运行的客户端也不会被拦住。

## 决定

是否必须升级由 bridge-agent-release-service 判断：它按平台、架构、系统版本选出客户端能安装的版本，
再套用平台管理员的策略。Relay 在设备连接时调用它的更新检查并执行结果。客户端负责：

- **上报身份。** `Capabilities` 带上客户端版本（`CARGO_PKG_VERSION`）、平台（`std::env::consts::OS`）、
  架构（`std::env::consts::ARCH`）和系统版本。系统版本与更新检查共用 `current_os_version()`，
  两边看到的值一致。
- **处理 Relay 的拒绝。** 收到 `UpdateRequired` 帧后，运行时进入 `update_required` 状态并停止重连，
  不按普通网络错误退避重试，直到被停止。
- **桌面端。**
  - 每小时复查一次更新；一旦需要强制升级，停止 Relay 连接、本地事件服务和受管 Connector，
    并显示强制升级页。
  - 运行时进入 `update_required` 时立即检查更新并执行同样的停止流程。更新检查失败或尚未判定强制时，
    仍以 Relay 的拒绝为准显示强制升级页。
  - 启动时离线、之后后台恢复检查发现必须升级时，不再只弹出窗口，同样停止业务。
- **命令行模式。** `run` 在运行时进入 `update_required` 时停止运行时、记录错误日志，并以错误退出。

## 依赖变动

`relay` git 依赖从 rev `8831f35`（relay 0.35.1）改为 relay 0.39.0 主线提交 `2d88ce0`，features 不变
（`default-features = false`、`device-channel`）。当前用户于 2026-10-31 确认（先确认到 0.38.0 提交，
选择修正方案 A 时确认到 0.39.0 提交）。两个 Cargo.lock 只改动 `relay` 一项。

## 发布

当前公开版本为 macOS 0.17.0、Windows/Linux 0.16.1。2026-11-03 当前用户明确确认：
“确认三平台发布 0.18.0”。本次 MINOR 补齐身份上报、运行中更新通知和升级界面处理；不改变设备协议版本。
已上线的 Relay 0.40.1 对缺失身份的已认证设备允许注册并记录告警；本次客户端发布不撤销该兼容行为，
也不修改发布服务的强制升级策略。

## 并发关闭与界面状态

- Runtime Manager 在收到必须升级通知或桌面端强制升级后，锁定本进程的启动限制；与启动、停止共用
  生命周期互斥，普通停止不会清除限制，升级后的新进程才拥有新的 Manager。
- Connector Process Manager 在整个启动期间持有读许可。必须升级时取得写许可，等待在途启动结束，
  阻止新启动，再停止已托管及已通过旧生命周期命令启动的应用；覆盖自动、UI、HTTP 和安装入口。
- 前端保存同一运行版本已经确认的必须升级决定。较晚返回的普通检查可以刷新下载信息，但不能清除
  强制升级页面或重新开放启动门禁。

验证包括收到通知后停止再启动、后台启动前已要求升级、Connector 在途启动与停止的交错，以及 React
更新检查晚于 Relay 通知返回和手动复查的情况。正式三平台制品仍须通过既有唯一发布工作流验证与签名。
