# 桌面启动与恢复契约

业务界面不能拥有客户端唯一的更新/修复入口。0.6.18 的回归来自 `useAppController` 中同步派生本地应用更新状态时，访问了稍后才初始化的 `const localAppUpdateStatus`。首次空配置渲染不触发，配置完成加载后才抛错；仅类型检查和空白配置测试无法发现。

## 责任边界

- 本地应用更新派生数据使用纯选择器，在任何同步消费者之前初始化，不依赖动作工厂的初始化顺序。
- HTML 自带可见的恢复面板和独立样式。恢复脚本不导入 React、业务控制器或业务样式；业务入口动态加载。
- 业务渲染边界、未捕获异常、模块加载失败、启动超时进入恢复页，错误只作为文本显示。业务 DNS 请求仍由业务处理，不能因正常可处理错误退出整个界面。
- 配置已加载且界面成功提交后才上报 `frontendReady`；后续渲染故障重新标记失败，保留启动诊断。
- 原生托盘与心跳监测位于 Rust 主进程；主窗口可见且持续无心跳时提示原生修复。系统 WebView 不响应时不依赖 JS 执行更新。
- 页面恢复和原生恢复调用同一官方签名更新器，并共享并发安装锁。不能绕过更新签名、安装安全检查或删除用户数据。
- 无网络时更新可能失败；进程无法启动或旧版本没有恢复入口时，必须使用官方完整安装包。不能承诺所有系统故障都可以在应用内恢复。

## 必须验证

`npm test` 覆盖真实 App 的非空配置、授权态、DNS 错误、配置错误、渲染异常与更新重试。`npm run build && npm run test:browser` 在构建产物上验证业务模块丢失、React 崩溃和全部 JS 丢失时仍有恢复说明。

`npm run test:native` 以独立应用标识、临时配置启动实际 Tauri WebView，验证非空配置界面、故障后的恢复页和真实 IPC。烟测入口只编入 debug 构建，不进入发行二进制，不启动设备服务。macOS 与 Windows 质量门禁和发行门禁均运行这些检查。

发行流水线额外用不可变的 0.6.18 MSI 作为回归夹具，覆盖安装本次签名 MSI，检查安装后二进制身份，以及不可读业务配置和应用数据逐字节保留。该测试只能在 GitHub Actions 临时 Windows runner 上运行。
